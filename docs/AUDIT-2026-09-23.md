# Consolidated audit report: Halo 1 (ESP32-C6 + BM5602), night of Sep 22 to 23

The audit was done read-only: no file in the repository was modified. There were four parts (protocol, documentation, code, transmission plan), then three adversarial cross-checks done with independent decoders. I also did one final recomputation (`scratchpad/audit/synthese/chk.py`).

**Key takeaway.** Our reading of the frame was shifted by 2 bits. The remote and the lamp use the BC5602's standard format (ESB type):
- preamble;
- true over-the-air address **63 FD F0 4F**;
- 9-bit PCF (packet control field);
- payload;
- CRC-16/CCITT with initial state **0xFFFF**.

The initial states 0xDFBE and 0xF55A are only artifacts. The failure of `txraw` is very probably explained by the address rather than the bytes, but this cause remains an assumption. The next test is to transmit in hardware mode, with automatic acknowledgement (auto-ACK).

Legend: **MEASURED** = recomputed from the captures; **ASSUMED** = interpretation or datasheet, not yet tested.

Payloads of the 9 asynchronous commands (`t3.py`), given as PID → payload:
- 0 → C4 C6; 2 → C4 C1; 3 → C4 A7;
- 0 → C4 B8; 3 → C4 FE; 1 → C4 C8;
- 2 → C4 FE; 2 → C4 D0; 1 → C4 9C.

On the FIFO side, byte 0 is mostly C4 or C5; 44, 85, and C3 are also seen, whose **meaning is unknown**.

### Remaining uncertainties, with no effect on the conclusion
- **Gap between the command and its acknowledgement.** It measures 104 bits from one window start to the next with the DPLL decoder (`t3.py`, 9 cases out of 9), 107 to 109 bits with the step-based decoders, and about 105 bits (32 + 73) in the FIFO. The silence between the two frames has no edges, so no decoder measures it exactly. The actual silence is about 23 to 28 bits (185 to 225 µs). This does not change the recommended ARD setting.
- **Where to place the "01" bits.** The CRC alone does not say whether they belong to the address. The same result is obtained with "state 0xDFBE on the window". Two arguments place them in the address: the preamble rule (1.5) and the exact return to 0xFFFF.
- **Datasheet address rule.** The note at ds.txt:1374-1376 ("MSB high 4-bit must be 0001xxxx or 1110xxxx") is followed by neither 0x63, nor 0x8F, nor the Halo 2 address. It does not appear to be applied in practice, or the transmitter is not a BC5602.
- **Channel 5.** It has not been independently re-checked; the captures were made on this channel.

## 2. What is false or doubtful, and the fix to apply

### 2.1 Conclusions from that night

| Claim | Verdict | Fix |
|---|---|---|
| Address 8F F7 C1 3C (written 3C C1 F7 8F) | **FALSE for transmitting.** It is only a window shifted by 2 bits. | True address: **63 FD F0 4F** over the air, **4F F0 FD 63** in the BM5602. Keep 8F F7 C1 3C only as the correlation pattern on receive. |
| Two initial states, 0xDFBE (commands) and 0xF55A (acknowledgements) | **FALSE.** Window artifact. | A single CRC, initial state 0xFFFF, starting at the true address. The 24- or 8-bit model only validates if the bit **following** the CRC is 0 (commands) or 1 (acknowledgements). This holds for 5 commands out of 9 and 9 acknowledgements out of 10 in asynchronous mode, and for 15/23 commands and 10/26 acknowledgements in the FIFO (`refute_lin/r2.py`, `refute_etats/t_fifo.py`). |
| "19 exact commands" | Figure true, meaning false. | These are exactly the frames whose following bit is 0 (`audit/compare.py`). With the correct model, about 31 commands out of 32 are exact. |
| Command = address + 1 header byte + 2 bytes + CRC | **FALSE by one bit.** | There are 23 bits (7 of PCF + 16 of payload) after the window, not 24. |
| Header [length 4][counter 2][type 2] | **FALSE.** | This byte groups the PCF's last 7 bits (low-order bits of the length, PID, NO_ACK) then the 1st bit of the payload (command) or CRC (acknowledgement). Conversion from the old H X Y notation: `p0 = (H&1)<<7 \| X>>1` and `p1 = (X&1)<<7 \| Y>>1`. So 21 89 FC gives C4 FE. |
| "About 107 bits" between the command and its acknowledgement | Approximate. | See the uncertainty above: 104 to 109 bits depending on the decoder. |
| Suspected 1-bit shift relative to the true PCF | **CONFIRMED in principle.** | The shift is 1 bit for the Halo 2 and **2 bits** for the Halo 1. |
| `txraw` had no effect, so the format was thought unknown | **Misinterpreted.** | The 39 bits transmitted after the window (`21 89 FC 0C 32`) were, **bit for bit**, a valid frame (PID 0, C4 FE, CRC 0619, MEASURED). The cause is ASSUMED but very likely: with 3C C1 F7 8F, our chip transmits the preamble 10101010, i.e. "10" instead of "01". This makes 2 wrong bits out of the 32 of the true address. Another point: 1800 copies with the same PID and the same CRC are discarded as duplicates by a receiver (ds.txt:1457-1466). |
| CC2500 verification of `txraw` | Inconclusive, as expected. | 0 occurrences of the window are found in `async-txraw*.log`, even tolerating 2 errors. The stream appears saturated or jammed (`audit/txscan.py`). This says nothing about the firmware. |
| 06 B9 21 BB 98 FF is a false positive | **CONFIRMED.** | It is an acknowledgement (PID 1). It stops after `06 B9 21`, and the following bytes vary from one capture to another. |

### 4.2 What the chip should transmit (calculated, `synthese/chk.py`)

The preamble 01010101 is automatic since the address starts with 0. The frame is then `63 FD F0 4F`, then the PCF `000010 PP 0`, then `C4 FE`, then the CRC. As seen from the 8F F7 C1 3C window (the usual CC2500 and FIFO notation):

| PID | CRC | Bytes after the window (last bit outside the frame) | Acknowledgement expected from the lamp (after the window) |
|---|---|---|---|
| 0 | 0619 | `21 89 FC 0C 32/33` | `02 F9 A4/A5` (CRC 7CD2) |
| 1 | 6879 | `25 89 FC D0 F2/F3` | `06 B9 20/21` (CRC 5C90) |
| 2 | DAD9 | `29 89 FD B5 B2/B3` (already captured) | `0A 78 AC/AD` (CRC 3C56) |
| 3 | B4B9 | `2D 89 FD 69 72/73` (already captured) | `0E 38 28/29` (CRC 1C14) |

The chip starts at PID 0 after the reset. It only increments it after an acknowledgement is received (ds.txt:1421-1431).

### 4.3 Steps

1. **Two-board bench, without the lamp.** The 2nd BM5602 plays the PRX, with the same address 4F F0 FD 63, ENAA=0x01, DPL, and CE=1. The CC2500 is in asynchronous capture.
   - Expected: TX_DS, then MAX_RT once the PRX is powered off.
   - On the CC2500, the bytes from the table and the PRX's acknowledgement should be found.
   - Record the NO_ACK of the acknowledgement transmitted by **our** chip. If it is 1, like the lamp's, that is a strong sign that the lamp uses a compatible BC5602.
   - This bench also checks that the PTX's turnaround to reception works without a reset (risk of false MAX_RT, see rf-findings point 5). **This point has never been verified.**
2. **Precautions before the lamp:**
   - remove the batteries from the remote (it has the same address, and an acknowledgement meant for it could be mistaken for ours);
   - lamp at half brightness;
   - never use the pairing address E2 08 00 B0 or a header byte of 0x0A;
   - only transmit payloads captured as-is;
   - **10 tries at most, spaced at least 500 ms apart**.
3. **Negative control** with the old address 3C C1 F7 8F, payload C4 FE, 10 tries. Expected: MAX_RT every time.
4. **Test** with 4F F0 FD 63, payload C4 FE, 10 tries, CC2500 in asynchronous capture.

| Test at MAX_RT, lamp's acknowledgement **visible** on the CC2500 | The lamp accepted the frame; it is **our** reception of the acknowledgement that fails (RX turnaround, NO_ACK polarity, AGC). See step 1. Also check whether the lamp reacted. |
| Test at MAX_RT, our frame correct on the CC2500, no acknowledgement | The model needs revisiting for the lamp: address, or a requirement specific to the lamp (pairing, listen window). Recheck channel 5 and the transmitted preamble. |
| Test at MAX_RT, frame absent or different on the CC2500 | Configuration problem on our side: compare against the step 1 bench. |
| Control at TX_DS | Anomaly: stray acknowledgement (remote still powered?) or unreliable TX_DS. Do not draw any conclusion from the test. |
| FIFO refused or timeout | The configuration sequence is incorrect: go back to the bench. |

**Fallback without auto-ACK** (calculated, not tested): hardware CRC off, address 4F F0 FD 63, and raw bytes transmitted after the address. The PID rotates from one send to the next, and the final 0x80 byte carries the CRC's last bit plus padding:
- PID 0: `08 62 7F 03 0C 80`
- PID 1: `09 62 7F 34 3C 80`
- PID 2: `0A 62 7F 6D 6C 80`
- PID 3: `0B 62 7F 5A 5C 80`

This mode gives no TX_DS verdict: only a visible reaction from the lamp counts as proof.
